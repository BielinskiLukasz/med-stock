# Requirements Archive: MedStock v1.0

**Archived:** 2026-07-19  
**Milestone:** v1.0  
**Core Value:** At a glance, from anywhere, know whether you already have a valid medicine — so you never overbuy and never miss an expired one.  
**Coverage:** 33/35 satisfied · 1 partial · 1 unsatisfied  
**Disposition:** Shipped with gaps. DATA-04 and DATA-02 merge deferred to v1.1 (see [v1.0-MILESTONE-AUDIT.md](../v1.0-MILESTONE-AUDIT.md))

## v1 Requirements

### Inventory (CRUD)

- [x] **INV-01**: User can add a medicine package with: name, category (predefined), location, expiration date, opened date, period-after-opening (value + unit), quantity remaining, quantity unit, notes — **Validated: Phase 1**
- [x] **INV-02**: User can edit any field of an existing medicine package — **Validated: Phase 1**
- [x] **INV-03**: User can view full details of a medicine package — **Validated: Phase 1**
- [x] **INV-04**: User can delete a medicine package (moves to Trash Bin, not permanently removed) — **Validated: Phase 1**
- [x] **INV-05**: App automatically calculates validity status from expiration date, opened date, and period-after-opening — combining both constraints (whichever expires first) — **Validated: Phase 1**
- [x] **INV-06**: Medicine package status is one of: Active, Opened, Expired, Used Up, Disposed, Archived — and updates automatically based on dates — **Validated: Phase 1**

### Search & Browse

- [x] **SRCH-01**: User can search medicines by name with partial/substring matching, from any screen — **Validated: Phase 2**
- [x] **SRCH-02**: Search results show stock + validity status in a single glance (no drill-down required for the critical question) — **Validated: Phase 2**
- [x] **SRCH-03**: User can filter the medicine list by category — **Validated: Phase 2**
- [x] **SRCH-04**: User can filter the medicine list by location — **Validated: Phase 2**
- [x] **SRCH-05**: User can filter the medicine list by status (Active, Opened, Expired, etc.) — **Validated: Phase 2**
- [x] **SRCH-06**: User can sort the medicine list by name, expiration date, or category — **Validated: Phase 2**

### Dashboard

- [x] **DASH-01**: Dashboard shows total medicine count — **Validated: Phase 2**
- [x] **DASH-02**: Dashboard shows expired medicines count as an alert card; tapping it opens a filtered list of expired medicines — **Validated: Phase 2**
- [x] **DASH-03**: Dashboard shows medicines expiring within 30 days as an alert card; tapping it opens the filtered list — **Validated: Phase 2**
- [x] **DASH-04**: Dashboard shows medicines that exceeded their period-after-opening as an alert card; tapping it opens the filtered list — **Validated: Phase 2**

### History & Audit

- [x] **HIST-01**: Every change to a medicine record (create, edit, delete, restore) is recorded with timestamp, changed field, old value, and new value — **Validated: Phase 2**
- [x] **HIST-02**: User can view the change history for a specific medicine package — **Validated: Phase 2**

### Trash Bin

- [x] **TRSH-01**: Deleted medicines appear in Trash Bin and are not permanently removed — **Validated: Phase 2**
- [x] **TRSH-02**: User can restore a medicine from the Trash Bin — **Validated: Phase 2**
- [x] **TRSH-03**: User can permanently delete a medicine from the Trash Bin — **Validated: Phase 2**
- [x] **TRSH-04**: Trash Bin preserves the full history of deleted items — **Validated: Phase 2**

### Locations

- [x] **LOC-01**: Predefined locations are available when adding/editing a medicine (Kitchen Drawer, Bathroom Cabinet, Bedroom Cabinet, Medicine Box, Travel Kit, Refrigerator, Living Room Cabinet, Other) — **Validated: Phase 1**
- [x] **LOC-02**: User can add a custom location — **Validated: Phase 1**
- [x] **LOC-03**: User can edit a custom location name — **Validated: Phase 1**
- [x] **LOC-04**: User can delete a custom location (medicines using it revert to "Other") — **Validated: Phase 1**
- [x] **LOC-05**: User can manage all locations from a dedicated Locations screen — **Validated: Phase 1**

### Data (Import / Export / Sync)

- [x] **DATA-01**: User can export the full inventory as a JSON file (medicines, locations, categories, history, settings) — **Validated: Phase 3**
- [x] **DATA-02**: User can import a JSON backup file to restore or merge inventory — **⚠ Partial: Phase 3** — Full replace delivered; last-write-wins merge not implemented (D-47). UAT decision: "Merge was always the intent; full replace is a gap." Deferred → v1.1 B-003.
- [x] **DATA-03**: User can import an existing inventory from a CSV file with an interactive column-mapping step — **Validated: Phase 3**
- [ ] **DATA-04**: User can trigger a "Sync Now" flow that guides them through exporting to / importing from a shared OneDrive folder — enabling two household members to share one inventory across their devices — **✗ Unsatisfied** — Only static SyncInstructions text delivered; no triggered flow. Deferred → v1.1 B-002.

### PWA & Offline

- [x] **PWA-01**: App works fully offline — all core features (search, add, edit, browse) function without any internet connection — **Validated: Phase 1**
- [x] **PWA-02**: App requests persistent storage on first launch to prevent iOS Safari 7-day automatic data eviction — **Validated: Phase 1**
- [x] **PWA-03**: App is installable as a PWA on Android, Windows, macOS, and Linux (home screen / taskbar) — **Validated: Phase 1**
- [x] **PWA-04**: App remains responsive with 1,000+ medicine packages — **Validated: Phase 1**

## Out of Scope

| Feature | Reason |
|---------|--------|
| Medication reminders / adherence tracking | Different product category (scheduling vs inventory); regulatory and UX complexity; users consult their doctor |
| Drug interaction checking | Requires maintained medical database; liability risk if data is stale |
| Photo capture and storage | Doesn't change core value (you still read the label); storage/sync burden; deferred to v2+ |
| OCR — expiry date, medicine name, barcode | Complex, error-prone, requires camera permissions; v1 is manual entry only |
| Automatic background sync | Manual "Sync Now" is sufficient for household use; background sync needs a backend or complex peer-to-peer |
| Multi-user profiles / household accounts | Auth complexity; current model is one shared inventory per device |
| Real-time multi-device sync | Requires backend or peer-to-peer; major architecture shift |
| Backend / cloud storage | Privacy requirement: all data stays on device |
| Medicine purchase tracking | Out of scope; MedStock is inventory, not purchasing history |
| Medicine consumption statistics | Out of scope for v1; may add in v2 based on user feedback |
| QR labels for storage locations | Out of scope; nice-to-have future idea |
